# PAT-007: Layered telemetry with pluggable backends

## Problem

A single telemetry backend does not fit all deployments. Developers need local logs, production needs OpenTelemetry or a proprietary observability platform, and product analytics may use PostHog or Langfuse.

## Solution

Use `tracing-subscriber` with a layered subscriber model: file + console + optional JSON/OpenTelemetry/Langfuse/PostHog layers. Each layer can be enabled independently via features or configuration. Telemetry events are emitted as normal logging/tracing calls and routed by the subscriber stack.

## Benefits

- No code changes needed to add a new telemetry sink.
- Standard `tracing`/`logging` macros keep instrumentation idiomatic.
- Feature flags keep production images small.

## Used by

- `block/goose` (`logging.rs`, `tracing/`, `otel/`, `posthog.rs`)
- ACC `telemetry/telemetry_service.py` already publishes `TelemetryEvent` to `EventBus`.

## ACC usage

Keep `TelemetryService` as the `EventBus` consumer and add pluggable exporter modules (console, file JSON, OpenTelemetry, Langfuse, PostHog) loaded from `SettingsSnapshot`. Each exporter subscribes to `telemetry.event` and transforms to its backend format.

## Compatibility

- Fits ACC authority model: **Yes**.
- Required ACC changes:
  - Add exporter plugin interface in `ai_command_center/telemetry/`.
  - Load exporters from settings; keep `TelemetryService` as orchestrator.
  - No new global state; exporters are services registered by `ServiceManager`.

## Priority

Low/Medium

## Risks

- Backend SDKs add dependencies and potential network blocking; use async queues.
- PII must be stripped before sending to third parties.
- Overlapping log/telemetry streams can create noise.
