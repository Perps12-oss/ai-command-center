# PAT-004: Tool Inspector / Confirmation Router Pipeline

## Problem

LLM-generated tool calls can be dangerous, leak data, or loop. The system needs a pluggable pipeline to inspect, filter, and request approval before execution.

## Solution

Goose uses a `ToolInspectionManager` with ordered inspectors:

1. SecurityInspector
2. EgressInspector
3. AdversaryInspector (LLM-based, opt-in)
4. PermissionInspector
5. RepetitionInspector

Each inspector returns findings. The `ToolConfirmationRouter` registers the request and emits an `action_required` message. User confirmation (allow once / always allow / deny / always deny) is awaited before `dispatch_tool_call` runs. Denials produce a synthetic tool response so the model can recover.

## Benefits

- Defense in depth.
- User remains in control of destructive actions.
- Permission preferences persist per tool.

## Used by

- block/goose (`crates/goose/src/agents/tool_execution.rs`, `agents/agent.rs`, `permission/`)

## ACC usage

ACC has `Execution Authority` and `Runtime Approval Model` (ADR-004). This pattern can refine the existing tool execution flow:

- `ToolExecutor` calls a `ToolInspectionService`.
- Findings publish `tool.inspection` events.
- `action_required` is routed through `AppState` to the UI.
- Confirmation produces `tool.approved` / `tool.denied`.

## Compatibility

- Strengthens ADR-004/ADR-006.
- Fits the EventBus/service hierarchy.

## Priority

High

## Risks

- Adding LLM-based adversary inspection is slow and costly.
- Must not duplicate existing runtime approval logic.
