# PAT-002: MCP Extension Manager with Multi-Transport

## Problem

Tools can come from local binaries, HTTP servers, inline scripts, or bundled code. The agent needs a uniform tool discovery and invocation layer.

## Solution

Goose uses a single `ExtensionManager` that supports multiple `ExtensionConfig` variants: stdio, streamable HTTP, Unix socket, builtin, platform, frontend, inline Python. The manager spawns/connects to an MCP server, caches the tool list, and routes calls.

## Benefits

- Broad ecosystem compatibility via MCP.
- Environment and secret substitution are centralized.
- Tool availability can be filtered per extension (`available_tools`).

## Used by

- block/goose (`crates/goose/src/agents/extension_manager.rs`, `extension.rs`)

## ACC usage

ACC's tool runtime (`ai_command_center/tools/tool_registry.py` / `tool_executor.py`) could support MCP providers as one of several sources. This is a future direction, not immediate.

## Compatibility

- Conflicts with ACC architecture if subprocesses become the execution authority.
- Requires a clear boundary: MCP extensions provide *tool definitions*, but `ToolExecutor` and `Execution Authority` remain ACC-owned.

## Priority

Medium

## Risks

- Subprocess sandboxing and trust model.
- Rust-specific implementation not directly portable.
- Could duplicate existing `plugins/` infrastructure.

## Status

Hold until ACC runtime provider interface is stable.
