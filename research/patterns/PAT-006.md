# PAT-006: Modular tool inspection and permission pipeline

## Problem

Tool calls need pre-execution checks for security, egress, adversarial inputs, and repetition, plus a user approval policy that can be per-tool and persisted.

## Solution

A `ToolInspectionManager` runs a list of pluggable inspectors over each tool call. Each inspector returns an `InspectionResult` with an action (`Allow`, `RequireApproval`, `Block`) and an optional message. A separate `PermissionManager` stores per-tool `PermissionLevel` (`AlwaysAllow`, `AllowOnce`, `Ask`, `NeverAllow`) and is updated by user choices.

## Benefits

- Security, egress, adversarial, and repetition checks are independent and testable.
- User approval is explicit and persistent.
- New inspectors can be added without touching the tool dispatch path.

## Used by

- `block/goose` (`tool_inspection.rs`, `security/`, `config/permission.rs`, `agents/tool_execution.rs`)
- Similar pre-execution hooks in ACC `ToolExecutorService`.

## ACC usage

Introduce a `ToolInspector` protocol called by `ToolExecutorService` before dispatching. Inspectors publish `telemetry.event` findings and can emit `action_required` events. `PermissionService` reads/writes per-tool levels from `SettingsRepository`. `tool.started` is only published after all inspectors allow.

## Compatibility

- Fits ACC authority model: **Yes**, with changes.
- Required ACC changes:
  - Add `ToolInspector` interface and `ToolInspectionManager`.
  - Integrate with existing `CommandSandbox` permission checks.
  - Persist permission choices in `SettingsRepository` or a new `permission` repository.

## Priority

Medium

## Risks

- False positives in security inspectors can frustrate users.
- Inspector ordering matters and must be deterministic.
- `AlwaysAllow` must be revocable.
