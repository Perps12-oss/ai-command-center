# PAT-001: Declarative Provider Registry with Inventory State

## Problem

A command center needs to support many LLM providers (OpenAI, Anthropic, Ollama, local, custom). Each provider has metadata, auth requirements, model lists, and a constructor. The UI needs to display configured and available providers without instantiating each one.

## Solution

Maintain a registry of provider *entries*. Each entry holds:

- Provider metadata (name, display name, default model, known models, config keys)
- `inventory_identity` resolver: stable ID for UI/model picker
- `inventory_configured` resolver: checks whether required secrets/envs are present
- Provider type: builtin, preferred, declarative
- Constructor closure/factory
- Optional cleanup hook

Declarative providers are loaded from JSON and registered with a generic engine-compatible constructor.

## Benefits

- UI can enumerate providers without constructing heavy clients.
- Custom providers can be added without code changes.
- Provider lifecycle (init, refresh, cleanup) is centralized.

## Used by

- block/goose (`crates/goose/src/providers/provider_registry.rs`, `init.rs`)

## ACC usage

ACC already has `OllamaService` and provider adapters. A `ProviderRegistry` could become a service in `ai_command_center/core` that publishes `provider.discovered` / `provider.configured` events. The UI reads from `AppState`.

## Compatibility

- Fits ACC authority model: providers are capabilities, not state owners.
- Requires defining a `Provider` contract and runtime provider interface.
- No ACC runtime code changes yet; this is a design pattern.

## Priority

High

## Risks

- Over-engineering if ACC only needs two providers.
- Must align with `docs/architecture/AGENT_RUNTIME_INTERFACE.md`.
