# INT-007: Telemetry backend layering

## Pattern reference

- **Pattern:** PAT-007 — Layered telemetry with pluggable backends
- **Source repository:** block/goose
- **Related RD:** RD-001

## Reason

ACC's `TelemetryService` already publishes `TelemetryEvent` objects to `EventBus`. Adding pluggable exporters would let deployments choose console logs, JSON files, OpenTelemetry, Langfuse, or PostHog without changing instrumentation.

## Proposed ACC usage

1. Define a `TelemetryExporter` protocol: `export(event: TelemetryEvent) -> None`.
2. Implement exporters: ConsoleExporter, FileJsonExporter, OpenTelemetryExporter, LangfuseExporter, PostHogExporter.
3. `TelemetryService` loads enabled exporters from `SettingsSnapshot` and subscribes to `telemetry.event`.
4. Exporters run asynchronously; failures in one exporter do not drop others.

## Files / modules affected

- `ai_command_center/telemetry/telemetry_service.py`
- `ai_command_center/telemetry/exporters/` (new)
- `ai_command_center/core/service_factory.py`
- `ai_command_center/core/settings/settings_schema.py`

## Estimated effort

Medium — 3-5 days per exporter; start with console/JSON.

## Dependencies

- Optional packages: `opentelemetry-api`, `langfuse`, `posthog`.
- Existing `TelemetryEvent` domain model.

## Risk assessment

- Low for console/JSON.
- Medium for external backends: network, PII, buffering.

## Constitutional compliance

- Does this violate the Constitution? **No**
- Does this weaken Execution Authority? **No**
- Does this weaken State Authority? **No**
- Does this duplicate existing systems? **No** — extends `TelemetryService`.
- Is there a simpler solution? **No** for multiple backends.

## Recommendation

`Adopt` after Architecture Review; implement backends incrementally.
