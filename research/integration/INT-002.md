# INT-002: MCP Capability Runtime Adapter

## Pattern reference

- **Pattern:** PAT-002 — MCP extension runtime with tool cache and environment denylist
- **Source repository:** block/goose
- **Related RD:** RD-001

## Reason

ACC's tool set is small and static. MCP lets ACC dynamically discover tools from sandboxed servers while preserving the canonical `TOOL_INVOKE` → `ToolExecutorService` → `EventBus` path.

## Proposed ACC usage

1. Add an `McpCapabilityRuntime` class implementing a capability runtime interface in `ai_command_center/runtime/`.
2. Store MCP extension configs in `SettingsSnapshot` or a repository.
3. `ToolExecutorService` delegates tool calls matching an MCP namespace to the adapter.
4. The adapter maintains a tool cache with version invalidation and an environment denylist.
5. Adapter publishes `tool.started`, `tool.completed`, `tool.failed` to `EventBus`.

## Files / modules affected

- `ai_command_center/services/tool_executor_service.py`
- `ai_command_center/tools/tool_registry.py` / `tool_executor.py`
- `ai_command_center/runtime/` (new `mcp_runtime.py`)
- `ai_command_center/core/service_factory.py`
- `ai_command_center/core/settings/settings_schema.py`

## Estimated effort

Medium — 5-7 days.

## Dependencies

- A Python MCP client SDK or an FFI bridge to `rmcp`.
- Subprocess lifecycle management utilities.
- Permission and sandbox models already in `CommandSandbox`.

## Risk assessment

- Medium: child process lifecycle, zombie prevention, hang detection.
- Medium: third-party MCP servers are untrusted; rely on permission and egress checks.
- Low: additive, does not replace existing shell tool path.

## Constitutional compliance

- Does this violate the Constitution? **No**
- Does this weaken Execution Authority? **No** — `ToolExecutorService` remains the orchestrator.
- Does this weaken State Authority? **No**
- Does this duplicate existing systems? **No** — it extends `ToolRegistry`.
- Is there a simpler solution? **No** for third-party dynamic tools.
