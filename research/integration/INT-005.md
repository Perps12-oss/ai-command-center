# INT-005: Tool inspection and permission pipeline enrichment

## Pattern reference

- **Pattern:** PAT-006 — Modular tool inspection and permission pipeline
- **Source repository:** block/goose
- **Related RD:** RD-001

## Reason

ACC's `ToolExecutorService` has basic permission checks. Adding pluggable inspectors would harden shell/MCP tool execution against prompt injection, egress, adversarial inputs, and repetitive loops without embedding logic in the executor.

## Proposed ACC usage

1. Define a `ToolInspector` protocol with `inspect(tool_name, arguments, session, context) -> InspectionResult`.
2. Implement inspectors: security (prompt injection), egress (network/domain), adversary (jailbreak), repetition.
3. `ToolExecutorService` calls `ToolInspectionManager.inspect()` before `tool_executor.execute()`.
4. `Allow` proceeds; `RequireApproval` emits `action_required` and waits; `Block` publishes `tool.failed`.
5. `PermissionService` persists per-tool levels in `SettingsRepository`.

## Files / modules affected

- `ai_command_center/services/tool_executor_service.py`
- `ai_command_center/tools/tool_executor.py`
- `ai_command_center/core/permissions/` (new)
- `ai_command_center/repositories/settings_repository.py`

## Estimated effort

Medium — 4-6 days.

## Dependencies

- Existing `CommandSandbox` and `ToolRegistry`.
- `action_required` event flow already present in ACC.

## Risk assessment

- Medium: false positives can block legitimate tools.
- Low: additive; existing simple allow/deny remains as fallback.

## Constitutional compliance

- Does this violate the Constitution? **No**
- Does this weaken Execution Authority? **No** — executor still decides.
- Does this weaken State Authority? **No**
- Does this duplicate existing systems? **No** — augments `ToolExecutorService`.
- Is there a simpler solution? **No** for multiple inspection categories.
